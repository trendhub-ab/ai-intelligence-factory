# AIIF｜事業目的・開発優先順位 正本（Business North Star）

**Authority:** Owner-approved, 2026-11-20  
**適用対象:** `trendhub-ab/ai-intelligence-factory`（旧Productionおよび残存資産）と `trendhub-ab/ai-intelligence-factory-next`（独立次世代実装）の**双方**。  
**正本の場所:** 本ファイル `docs/AIIF_BUSINESS_NORTH_STAR.md` を一つだけ維持する。Next側には独立した競合正本を作らず、本書への参照を置く。  
**変更権限:** 方針変更にはオーナーの明示承認と専用PRを必要とする。コード改修・CI GREEN・過去の実験結果だけで書き換えない。

> **North Star:** AI・技術の変化を根拠付きで収集・評価し、無料noteを通じて読者の興味と信頼を得て、月額課金の「このAI、使える！」を判断する情報商品へ転換する。低コストで継続価値と持続可能な収益をつくる。記事生成・投稿自動化・DB件数・CI PASSは手段であり、事業目的ではない。

## 1. 既存契約との優先関係

- **現行の有料商品・ICP・価格・販売導線・会員表示の詳細な正本**は [PAID_PRODUCT_CONTRACT.md](../PAID_PRODUCT_CONTRACT.md)（Run307 Use-Decision）であり、本書はこれを変更しない。
- **Nextの独立開発・編集品質・実験と旧Productionの境界**は [AIIF Next docs/CANONICAL_ARCHITECTURE.md](https://github.com/trendhub-ab/ai-intelligence-factory-next/blob/main/docs/CANONICAL_ARCHITECTURE.md) と [docs/DEVELOPMENT_CONTRACT.md](https://github.com/trendhub-ab/ai-intelligence-factory-next/blob/main/docs/DEVELOPMENT_CONTRACT.md) に従う。
- Evidence/Fact/Publication/Notionアクセスと秘密情報の既存安全契約を維持する（例: [NOTION_ACCESS_POLICY.md](../NOTION_ACCESS_POLICY.md)、[V1_RETIRED.md](../V1_RETIRED.md)）。
- 契約同士が衝突する場合は、勝手な移行・緩和・仕様の取り込みを行わず、論点と影響を明示してオーナーの判断を得る。本書が旧Productionの実行・復活やNextの本番移行を承認したことにはならない。

## 2. 誰に、何を売るのか

- **初期ICP:** AI・Web・業務システム等を開発・導入・必要に応じて提案するフリーランス、個人事業主、1〜3名規模の小規模事業者（詳細は商品正本）。
- **販売する価値:** ニュースやDBの件数ではなく、一次情報・比較・条件・リスク・履歴を使って「このAI、使える！」という判断までの時間と手間を減らすこと。
- **基本導線（変更不可、変更時はオーナー承認）:** 無料note → 固定LP → noteメンバーシップ → Notion会員ホーム → Decision Brief／Decision Intelligence DB／Decision・Action Asset。
- **無料noteの役割:** 興味・理解・共感・信頼と見込み会員の獲得。読み物として面白く自然な日本語、テーマ固有の発見、正確な一次情報、適切なCTAを重視する。品質を意図的に下げない。
- **有料商品の役割:** 読み物の焼き直しではなく、Use-Decisionに必要な比較・証拠・利用条件・リスク・変化・「次の一手」を継続提供する。必要に応じて判断メモや簡易検証条件も届ける。
- **価格と検証:** 現行の標準価格は**月額1,980円**。最初の事業検証は**実有料顧客10人**（売上目標や転換率を根拠なく捏造しない）。継続率、再利用、解約理由を測る。詳細な価格変更や100人以降の計画は商品正本と別承認を参照する。
- **損益・コスト:** API利用料のみでなく、人手編集、再実行、障害対応、配送失敗、保守を含めた**合格記事・有効な判断情報・有料継続会員あたりの総コスト**で評価する。ROIを創作しない。

## 3. 一次Evidenceから、無料・有料の二系統へ

```text
一次情報の収集（GitHub / arXiv / Hacker News / OfficialVendor 等）
  → Source / Evidence検証・重複排除・情報更新の追跡
  → 独立Fact / Editorial / Decision 評価
      ├─ 無料：読者向けWriter → Fact/編集レビュー → Content Intelligence DB
      │        → アイキャッチ → note投稿管理DB → 非公開下書き保存・再読込検証
      │        → 人間による公開承認・公開 → CTA → 固定LP
      └─ 有料：Technology/Decision/Evidence/History → Decision Intelligence
               → Decision Brief / Action Asset → Notion会員ホーム
  → noteメンバーシップ入会・継続利用 → 事業効果の検証・改善
```

- Evidenceは共有するが、**無料記事のWriter人格・感情表現をDecision/Evidenceの事実・スコアに侵入させない**。
- Content Intelligence DBは無料記事原稿の監査・品質・正本、note投稿管理DBはReady通過後の配送状態、下書きID・公開URLの管理。内部のNotion DBと会員向けNotion DBを混同しない。
- 原稿・画像・品質承認・配送先・安定した記事IDを結び、欠落や重複のない保存と再読込確認を行う。Notionの更新が欠けているのに「記事一連の配送完了」としない。
- **非公開下書きの自動保存は必要機能**。公開は既存の商品正本どおり human-only。自動下書き完成を一般公開の承認と取り違えない。
- **会員向け価値の継続更新**も必要機能。無料記事の自動投稿が完成しても、それだけでAIIF事業完了とはしない。
- AIIF Nextと旧Productionは独立させる。既存のnote/Notion資産を利用する場合、アクセス権限・ID・副作用・重複防止・切替・復旧を個別に検証する。**旧Productionへの強制再統合、旧V1の復活、無断停止は禁止**。

## 4. 開発の優先順位と棄却条件

1. **顧客価値と売上仮説:** 「誰が、何の判断に、なぜ月額を払うか」、無料記事から有料商品への導線、継続利用をまず確認。
2. **Evidenceと品質:** 正確な一次資料、独立したFact/編集レビュー、自然で面白い日本語、決定に使える有料情報の再現性。
3. **二系統のデータ蓄積と配送:** Notion正本・note下書き・アイキャッチ・会員面を、既存資産を最大利用して**最小コストで一連に連結**する。
4. **実環境E2Eと計測:** 作成→保存→読戻し→DB同期→公開（人間承認）→加入→継続の現物を検証。CI GREENや診断ログだけを成果とみなさない。
5. **効率化・スケール:** 上記を阻害している実測ボトルネックだけ改善。汎用的な新基盤・診断機能・PRの量を成果とみなさない。

以下の提案は**原則として停止・再評価**する：
- 収益・顧客体験に結び付かない局所的な修復の連鎖、同じ問題の調査だけを延々継続すること。
- 既存機能があるのに同種機能・DB・公開経路を新設し、データの正本や保守先を二重化すること。
- noteへの下書き保存だけを完成条件とし、Notion蓄積・アイキャッチ・品質Ready・会員向けDBを切り離したまま事業上の完成と報告すること。
- Provider/Secret/Production/Publication権限を暗黙にNextへ継承すること。
- 機械テストやモデル採点だけを読者の満足・販売・継続の実証に置き換えること。

## 5. 成功の判断指標

| 階層 | 必ず追跡する実測値 |
| --- | --- |
| 記事の品質 | 独立Fact/編集レビュー通過率、人手修正時間、一次根拠の被覆 |
| 無料配送 | Ready→Notion正本→アイキャッチ→note下書き→読戻し→公開の実際の成功件数・失敗理由・重複件数 |
| 有料商品 | Decision/History/Brief更新の鮮度、利用可能な判断数、利用時の根拠・次の一手 |
| 顧客獲得 | note閲覧→LP→メンバーシップ入会の実測転換、**有料顧客10人**への到達 |
| 継続・収益 | 有料継続率、解約理由、月額売上、粗利益、運用総費用、顧客の利用継続 |
| リスク | 誤情報・非公開情報漏えい・無断公開・重複配送・権限事故はゼロ容認 |

測定できていない数値は **未計測** と記す。記事本数とCI通過数を売上・顧客満足の代用にしない。

## 6. すべての開発PRの必須確認

作業開始前に本書、`PAID_PRODUCT_CONTRACT.md`、対象リポジトリの開発契約、既存の実装状況を読む。**既存資産を確認してから新しいコードを提案する。**

各PRでは少なくとも次を説明する：
1. **事業目的:** 本変更が無料記事の集客／有料商品／会員の継続価値のどれを改善するか（「維持・安全確保」も理由を具体化）。
2. **顧客価値と測定:** 顧客がどう得をするか、実環境で何を見て成功とするか。未計測は未計測と書く。
3. **既存資産・重複:** 再利用する実装/DB、重複・正本の分岐が起きない理由。
4. **E2Eの位置:** AIIF Next → Evidence/Review → 無料/有料Notion → note保存/会員面までのどの区間か、**未接続区間**はどこか。
5. **安全と費用:** Fact、Publication human-only、認証・権限、旧系隔離、Provider呼出しと追加コスト、ロールバック。
6. **オーナー承認:** mainのマージ、ライブ実行、一般公開、販売条件変更、旧Production切替は個別承認。

レビュー時に「局所機能は動いたが事業上の完成ではない」を明示し、未完成区間を隠さない。

## 7. 人とCIによる参照の強制

- 両repoルートの `AGENTS.md` はこのファイルを**最初に読む**ことを指定する。
- 両repoのPRテンプレートは第6節の6項目を要求する。
- 両repoで事業方針ガードCIを**全PRとmain push**へ接続し、参照ファイルの削除・変更漏れ・PRの検討記入漏れを検出する。
- CIは記述形式・存在・最低限の参照を検査できるが、顧客価値そのものは証明できない。実環境検証と人間のレビューを省略できない。
- 本書を変更する場合はオーナーが明示承認した専用PRで行い、両repoの参照を同期する。通常の作業中に黙って改稿しない。

**最終判断:** 「この変更で、無料読者または有料会員の価値が上がり、収益・継続に一歩近づくか。既存資産を活かし、低コストで実証できるか。」に答えられない仕事は、実装より先に事業目的を再検討する。
